# 听感层：面向听众的入口改版方案

> 版本 v1 · 2026-10-24 · 依据：DJ 朋友的使用反馈 + 对 `index.html` / `app.js` / `audio.js` / `data/*` 的逐项体检
>
> 配套原型：`docs/prototype/listen-entry.html`。单文件、无依赖，可直接双击打开。已跑通：27 个风格、13 个合成配方、1080×1440 卡片导出、DJ 过渡检查；320 / 360 / 390 / 414 / 768 / 1024 / 1280 / 1440 / 1920 九档宽度零横向溢出，无运行时报错。原型里的配方与文案是示例，不是终稿。

---

## 0. 摘要

**一句话问题**：现在的站点默认读者是「想做歌的人」——首页第一句是「先做出一段 Loop，再谈风格」，导航第一项是制作课，图谱第一屏是 24 个大族（另有 5 个补遗桶）和 1376 条。一个只想搞懂「今晚听到的是什么」的人，在这里找不到第一步。

**方案不是重做，是加一层**：在制作线旁边加一条**听感线**，用 `BPM × 律动` 代替流派分类作为第一层入口，用「一句话 + 三个可听特征」代替术语作为解释单位，用「一张能发到群里的图」代替链接作为传播单位。所有听感页最后都回到现有条目页和课程页。

五件事：

| # | 做什么 | 解决的反馈 | 主要成本 |
| --- | --- | --- | --- |
| 1 | **三问入口**：速度带 × 律动型 × 低频形态 → 16 格矩阵 | 「不知道点哪」 | 1 份编辑数据（约 120 条） |
| 2 | **三层解释**：L1 一句人话 / L2 三个听点 / L3 术语原文（折叠） | 「术语太多」 | 60 条文案 |
| 3 | **配方试听**：一个合成引擎 + 60 个数据配方，覆盖 1376 条（三档回退） | 「只有 10 个能听」 | 60 个配方 + 1 个渲染器 |
| 4 | **分享卡**：Canvas 生成 1080×1440 图卡，长按保存进群 | 「发出去只有一行灰字」 | 1 个渲染器 + 60 张 OG 预渲染 |
| 5 | **DJ 三件套**：过渡检查器 / BPM 邻接表 / 离线速查卡 | 「现场不敢用」 | 规则表 + PWA |

**不改三件事**：制作课主线（22 课 9 模块）、知识库数据结构（1376 条是资产，不为易懂而删）、Club Rig 视觉语言（新组件沿用，不另起一套）。

**一个必须先做的前置**：域名 + HTTPS。现在线上是 `http://47.94.222.72/music/`，微信里打开会带风险提示，且没有域名就无法配置公众号 JS 安全域名，分享链路的天花板被锁死。这件事 0.5 人日，但决定第 4 项的全部效果。

**四周路线**：第 1 周入口 + 24 族配方 + 文案（可独立上线）；第 2 周 60 配方 + 分享卡 + OG；第 3 周 DJ 三件套；第 4 周识曲 P1 或内容补全。

**为什么没做这两项。** Set 曲线要拖 8 段、导出图片、还要和邻接表共用数据，工作量接近前面半个 sprint，而它只服务「准备 set」这一个场景；先把过渡检查和邻接表跑稳更划算。识曲 P1 需要 onset + 自相关 + 拍型分类，代码量不小，且精度必须用真实录音验证——用合成信号验收会得出漂亮但没意义的结论。这两项留在方案里，等前面四项有真实使用数据再决定。

**两处必须知道的取舍。**
1. 矩阵 4 × 4 里有 5 格是空的（慢/碎、中/半拍、中/碎、中/切分、极快/切分）。这是真实分布，不是没做完——中速的舞曲几乎都是四拍落地。页面写「少见」，不硬凑数据。
2. 60 条风格的 BPM 大多是「编辑推断」（区间中点），卡片和面板都标了来源。只有原文明确写了数字的才标「原文明确」。**推断值不能当唱片上的数字用。**

## 1. 现状体检

### 1.1 站点现在服务谁

`README.md` 写得很清楚：「以制作课 + 知识库为双核心」。这不是缺点，是定位。问题在于**这个定位没有给听众留门**：

- 首页唯一主按钮是「开始第一课」（`app.js:1228`），它通向 DAW 和工程模板。
- 导航五项：制作课 / 知识库 / 图谱 / 练习 / 实验室——四个是制作者工具，一个是分类树。
- 条目页第一屏是「大族 chip + 别名 + BPM 尺 + 例曲数 + 原文行号 L1135」，这是研究者视图，不是听众视图。

DJ 朋友的反馈翻译成产品语言就是：**入口成本 > 收益预期**。他不是不想看，是不知道先看哪个。

### 1.2 六个断点（都能在代码里指出位置）

| # | 现象 | 证据 | 影响 | 修法 |
| --- | --- | --- | --- | --- |
| 1 | **入口只有一个方向** | 首页 `hero-actions` 只有「开始第一课 / 打开知识库」 | 听众进来 5 秒内找不到自己的路 | 首页加第二扇门「我不知道这是什么风格」→ 三问 |
| 2 | **术语先于听感出现** | 条目页正文是原文整理，`Sidechain`、`Supersaw` 直接出现；术语手册在独立页 `#/guide/glossary`，不在阅读路径上 | 读到第三个词就退出 | L1/L2/L3 分层，术语折叠到第三层并链到术语页 |
| 3 | **能听的只有 10 条，实际生效 9 条** | `audio.js:716` `DEMOS` 共 10 个；`demoForEntry()` 按 `entryId` 精确匹配，而 `DEMOS.techno.entryId = 'f-2077'` 是大族 id，条目页永远匹配不到 | 1367 条（99%）没有任何声音；Techno 这段等于白做 | 配方表 + 三级回退（专属 → 大族 → 最近祖先） |
| 4 | **BPM 覆盖率 13%，且大族内跨度失控** | `data/kb.js` 中 181/1376 有 BPM；HDM 族 100–300、Trance 族 90–250、House 族 100–180 | 「用 BPM 找风格」这件事现在做不了 | 大族级 BPM 带 + 条目窄区间 + 来源标注 |
| 5 | **分享出去是一条没有信息的链接** | 单页 SPA + hash 路由；`index.html` 无任何 `og:` 标签；线上是 IP + http | 微信群/朋友圈里只有一行灰字，点开率极低 | 图卡（主）+ OG 预渲染（辅）+ 域名 |
| 6 | **现场场景没有对应视图** | 条目页信息密度是研究者级；无离线能力 | DJ 在台上不敢打开 | 速查卡（一屏一风格 + 离线和常亮） |

第 3、4 条是**数据问题不是设计问题**，也最容易在两周内解决，收益最大。

### 1.3 三个已经存在、不要重造的资产

- **`audio.js` 的合成能力**：kick / clap / hat / bass / chord / pluck / lead / vocal / riser / impact 十个音色函数已经写好，配器逻辑成熟。缺的不是合成器，是「把配器变成数据」。
- **`DEMOS` 的十段骨架**：Bigroom、Electro、Deep、Uplifting、Techno、Trap、Future Bass、Dubstep、Hardstyle、Future Rave，每段都有一句 `blurb` 和一个特征动作。这十段就是配方的种子。
- **`curated.js` 的编辑层**：`tenStyles` 已经有 `signature / tips / tracks / caveat` 四个字段，是「编辑内容不污染生成数据」的现成范式。听感层照这个模式加一个 `data/listen.js` 即可，**不动 `kb.js`**。

## 2. 设计判断：为什么是 BPM × 律动

### 2.1 分类名不是入口

「Tech House 和 Deep Tech 有什么区别」这个问题，只有已经入门的人才问得出来。没入门的人问的是「这个为什么听起来跟刚才那个不一样」。

分类名是**结论**，不是**线索**。线索必须是用户能自己数、自己指的东西：

- 一分钟多少拍 → 可以数
- 鼓是每拍一脚还是两拍一下 → 可以点头确认
- 低音是一直垫着还是一下一下 → 可以用嘴模仿

这三件事不需要任何术语，就能把 90% 的俱乐部场景分到 5 个候选以内。这就是入口。

### 2.2 三分法 → 16 格

**维度一：速度带**（4 档，按身体感受命名，不按流派）

| 带 | BPM | 一句话 |
| --- | --- | --- |
| 慢 | 60–110 | 可以走路 |
| 中 | 110–128 | 可以点头 |
| 快 | 128–140 | 想抬脚 |
| 极快 | 140–200 | 只能跳 |

> 下限定在 60 而不是 90：Lo-fi、Downtempo、Trip Hop、Ambient 都在 80 上下，卡在 90 会把它们全部挤出矩阵。

**维度二：落地方式**（4 类，用拟声词命名）

| 类型 | 术语（小字附注） | 听感 |
| --- | --- | --- |
| 每拍一脚 | Four-on-the-floor | 咚 · 咚 · 咚 · 咚，像心跳 |
| 两拍一下 | Half-time / Two-step | 咚 ——— 咚 ———，像走路 |
| 碎的 | Breakbeat | 咚哒咚咚哒，像下雨 |
| 切开的 | Syncopated | 咚—哒，不在正拍上，有点拖 |

**维度三（可选，用于收窄）**：低频形态——「一直垫着」/「一下一下点」/「几乎没有」。

前两维交叉得到 16 格，每格 2–6 个代表风格。第三维只在格内做二次筛选。

### 2.3 必须制造的一次顿悟

**Trap 是 140 BPM，Hardstyle 是 150 BPM，数字只差 7，身体感受完全相反。**

Trap 的鼓是「两拍一下」，所以听起来像 70；Hardstyle 是「每拍一脚」，所以听起来像 150 还要快。这个反差是整个站点最好的教学素材，也是最容易被转发的内容（见 §5.3 对比卡）。

设计上要刻意把它做出来：在矩阵里把 Trap 和 Hardstyle 放在相邻格，点任意一个都能一键切到另一个做 A/B。用户在这里花 20 秒，就永久理解了「BPM 不等于快慢，律动才决定身体」。

### 2.4 术语不是删掉，是延后 15 秒

原文不动，只在它前面加两道缓冲：

```
L1  一句人话        18 字以内，说身体反应
L2  三个听点        每个 12 字以内，说"听哪里"
L3  术语与源流      折叠，默认收起，展开就是现有正文
```

术语第一次出现的位置，从「第一屏」挪到「用户已经听过之后」。这不是妥协，是教学顺序：**先有听觉锚点，术语才有挂靠的地方**。

## 3. 内容模型：L1 / L2 / L3

### 3.1 字段与字数预算

| 层 | 字段 | 字数 | 规则 |
| --- | --- | --- | --- |
| L1 | `oneLine` | ≤ 18 字 | 只写身体反应或场景，**禁止出现流派名、年代、地名** |
| L2 | `hear[3]` | 每条 ≤ 12 字 | 固定顺序：鼓 → 低音 → 空间；每条对应一个可 solo 的声部 |
| L2+ | `when` | ≤ 20 字 | 「什么时候会听到」，给非专业听众一个记忆钩子 |
| L3 | 现有 `description` | 不限 | 原文照录，加来源标记 |

`oneLine` 的禁用词表：`融合`、` influenced`、`场景`、`实验性`、`地下`、`先锋`、`解构`——这些词对目标读者零信息量。

### 3.2 十二个风格的成稿文案

可直接落库，也可作为其余 48 条的写作模板。

| 风格 | L1 一句人话 | L2 听哪里（鼓 / 低音 / 空间） | when 什么时候会听到 |
| --- | --- | --- | --- |
| Techno | 一条不会停的传送带，你只能跟着走。 | 每拍一脚，几乎没有起伏 / 低音在反拍上一下一下 / 很干，几乎没有混响 | 凌晨两点以后，灯全灭的时候 |
| Deep House | 有人在你耳边说话，鼓在下面轻轻推。 | 每拍一脚但很软 / 低音闷，只走两三个音 / 混响多，像在小房间 | 日落后的露台，第一杯酒 |
| Bigroom House | 体育馆那么大的房间，一秒钟把你举起来。 | 每拍一脚，Kick 特别大 / 低音只补空档 / 混响很宽，像在山谷 | 音乐节主舞台，天黑了以后 |
| Uplifting Trance | 先把你举到半空，再松手。 | 每拍一脚，速度偏快 / 低音持续铺底 / 混响很长，有旋律在绕 | 日出前那一个小时 |
| Trap | 鼓很慢，帽子很快，头会自己点。 | 两拍一下（听起来像 70）/ 808 很低，会滑音 / 高频密，空间干 | 夜店前半场，或者车上 |
| Dubstep | 低音像一头会呼吸的机器。 | 两拍一下，中间空一格 / 低音在抖、在变形 / 空间忽大忽小 | 有人想甩头的时候 |
| Drum & Bass | 心跳被调到 174，脚步跟着跑。 | 碎的，两拍里塞三下 / 低音又长又低 / 高频碎，像下雨 | 凌晨四点，剩下的人都还在 |
| Hardstyle | 每一脚都踹在胸口。 | 每拍一脚，Kick 是失真的 / 低音先吸后打，是反的 / 空间硬，没什么混响 | 大型室内场，灯光全开 |
| Amapiano | 懒懒的鼓，加一声很远的木鱼。 | 每拍一脚但留白很多 / 低音是「咚—咚」的木质感 / 混响松，像在户外 | 下午的派对，有人还没醒 |
| Afro House | 一群人在同一个节奏里走夜路。 | 每拍一脚，鼓有手打的感觉 / 低音跟着人声走 / 空间开阔，有回声 | 海边、日落、一群人 |
| Hyperpop | 所有东西都调得太快、太亮、太甜。 | 鼓是拼的，位置不固定 / 低音短，被切碎 / 全是效果，没有「房间」 | 耳机里，刷短视频的时候 |
| Breakcore | 鼓被撕碎，然后撒在你脸上。 | 碎的，速度极快 / 低音被切片 / 没有空间，全是撞击 | 耳机里，凌晨三点，不想睡 |

最后一条是刻意的：**不是所有风格都属于俱乐部**。承认这一点比假装 1376 条都能在舞池里听到更可信，也避免用户拿着 Breakcore 去问 DJ「放这个吗」。

### 3.3 术语 → 人话对照表

用在三个地方：条目页的 `title` 提示、分享卡的脚注、术语页顶部的「先看这个」。

| 术语 | 一句人话 | 在哪听到 |
| --- | --- | --- |
| Four-on-the-floor | 每一拍踩一脚，像心跳 | 数「1-2-3-4」，每下都有鼓 |
| Off-beat | 鼓的空档里补一下 | 「咚—次—咚—次」里的「次」 |
| Sidechain | 鼓一响，别的声音自动让开 | Drop 里和弦一起一伏，像呼吸 |
| Supersaw | 十几层一样的音叠起来，像一大片弦 | Trance / Bigroom 的宽和弦 |
| Reese Bass | 两个低音互相打架，嗡嗡的 | DnB / Dubstep 那种「呜——」 |
| Wobble | 低音被一只手拧来拧去 | Dubstep 的「哇哇哇」 |
| Acid | 一条滑来滑去、越来越尖的合成线 | Techno 里像水管的声音 |
| 808 | 又低又长、会拐弯的底鼓 | Trap 的「咚——」 |
| Half-time | 鼓慢一半，但速度没变 | 数起来像 70，其实是 140 |
| Breakbeat | 鼓不是每拍一脚，是碎的 | 像有人在打鼓，不像机器 |
| Build-up | 所有东西往上走，然后突然停 | Drop 前那 8 小节 |
| Drop | 全部砸下来的那一下 | 全场举手的地方 |
| Breakdown | 鼓撤走，只剩旋律 | 用来喘气的那一段 |
| Riser | 往上扫的「嘶——」 | Build-up 里一直响的那个 |
| Stab | 一下就没的短和弦 | House 里「哒」的一声 |
| Pluck | 拨一下就没的音色 | 琶音，一颗一颗的 |
| Pad | 铺在底下的长音 | Breakdown、慢歌 |
| Swing | 让鼓「晚一点」，听起来更松 | 不精确、有点拖 |
| Quantize | 把所有音对齐到格子上 | 听起来「太整齐」 |
| Limiter | 把超过天花板的音量压回去 | 很响，但不破 |

### 3.4 数据落在哪

**新增 `data/listen.js`（手工维护，不进构建）**，键为 `entryId`。理由：

- `data/kb.js` / `data/web.js` 是 `scripts/build-data.mjs` 的生成物，手改会被覆盖；
- `curated.js` 已经证明「生成数据 + 编辑层」两层并行可行；
- 听感层有 `entryId` 就可以单向依赖知识库，不反向污染。

```js
// data/listen.js —— 听感层（手工维护）
window.KB_LISTEN = {
  version: 1,
  updated: '2026-10-24',
  // 大族默认：条目没有专属数据时的兜底
  families: {
    'f-2077': { band: 'fast', groove: 'floor', lowEnd: 'pulse', fp: 'techno' },
    'f-165':  { band: 'mid',  groove: 'floor', lowEnd: 'sustain', fp: 'deephouse' },
    // … 24 条
  },
  // 条目级：只写与兜底不同的部分（稀疏覆盖）
  entries: {
    'g-1135': {                       // Deep House
      oneLine: '有人在你耳边说话，鼓在下面轻轻推。',
      hear: ['每拍一脚但很软', '低音闷，只走两三个音', '混响多，像在小房间'],
      when: '日落后的露台，第一杯酒',
      bpm: { min: 110, max: 125, source: 'editorial' },
      band: 'mid', groove: 'floor', lowEnd: 'sustain',
      fp: 'deephouse',                // 专属配方
    },
    'g-1581': { /* Bigroom … */ },
  },
};
```

`source` 三值：`source`（原文明确写出数字）/ `editorial`（编辑按代表曲与乐理推断）/ `family`（继承大族默认）。页面必须显示来源，禁止把推断值渲染成与原文同级的事实——这一点现有代码已经做对了（`bpm-source-note`），继续沿用。

### 3.5 覆盖目标

| 层 | 目标 | 数量 | 验收 |
| --- | --- | --- | --- |
| 大族 | 全部有 band / groove / 默认配方 | 24 | 构建脚本断言 24/24 |
| 高频风格 | 有专属 L1 + 三个听点 + 窄 BPM 区间 | 60 | 断言 60/60，且 L1 ≤ 18 字 |
| 其余条目 | 继承大族，页面标注「同族参考」 | 剩余 | 抽检 20 条无空白 |

60 条是「覆盖 90% 实际对话」的最小集：House 12 条、Techno 8、Trance 6、Bass 8、Breakbeat 6、HDM 6、Hip-Hop/Trap 6、其余 8。

## 4. 试听：一个引擎，三档覆盖

### 4.1 为什么不做真音频

| 方案 | 版权 | 体积 | 离线 | 结论 |
| --- | --- | --- | --- | --- |
| 托管 30 秒原曲片段 | 需逐首授权，个人站不可行 | 60 条 × 500KB ≈ 30MB | 不行 | 否 |
| 嵌入 YouTube / Spotify | 合规，但国内网络不可用、加载慢 | — | 不行 | 否 |
| 嵌入 B 站视频 | 合规、可播 | 需逐条找视频 | 不行 | 作补充出口 |
| **合成配方** | 无版权问题（原创合成） | 60 条配方 ≈ 10KB gzip | 可以 | **是** |

现有 README 已经明确「所有试听由 Web Audio 实时合成，不使用原曲录音」，这条原则继续守住。合成示例的作用不是替代原曲，是**让人听清骨架**——这恰好是科普需要的，而不是听整首歌需要的。

### 4.2 配方数据模型

把 `DEMOS` 里十个 `play()` 函数改成声明式数据。一个配方 = 一组图案字符串 + 一组音色参数：

```js
{
  id: 'techno',
  bpm: 132,
  key: 33,                        // MIDI，A1
  kick:  { steps: 'x---x---x---x---', gain: .88, decay: .32, drive: 0 },
  clap:  { steps: '----x-------x---', gain: .12 },
  hat:   { steps: '--x---x---x---x-', gain: .04, open: false },
  bass:  { steps: '--x---x---x---x-', wave: 'saw', cutoff: 900, env: 'pluck',
           gain: .14, len: .16, lfo: 5, lfoDepth: 140 },
  chord: { steps: 'x-------x-------', type: 'min', wave: 'saw', detune: 4,
           cutoff: 900, gain: .028, len: 1.9, rev: .3, attack: .3 },
  space: { rev: .22, delay: 0 },
  layers: ['drums', 'bass', 'chord'],
  signature: '每 8 小节只改一个参数',   // 这一段用来讲"它靠什么推进"
  hookStep: [7, 15],                   // 签名动作落点（第 7、15 格）
}
```

图案用 16 字符表示一小节，和站点「一小节 = 16 格」的语法完全一致，编辑时可以直接对着格子读。**配方是数据不是代码**，这是能扩到 60 条的前提。

### 4.3 三档覆盖

| 档 | 内容 | 数量 | 页面文案 |
| --- | --- | --- | --- |
| T1 | 大族签名循环 | 24 | 「House 这一族的声音」 |
| T2 | 高频风格专属 | 60（含 T1） | 「Techno 的骨架」 |
| T3 | 继承最近祖先 | 其余 1316 | 「同族示例：Techno」+ 一行说明 |

T3 的标注不能省。用户点开「Belgian Techno」听到的是 Techno 的配方，必须一眼看出来这不是「Belgian Techno 特有的东西」——否则就是在教错东西，比没有声音更糟。

回退算法很简单：`专属 fp → 最近有 fp 的祖先（沿 pathIds 上溯）→ 大族默认 fp`。现有 `pathIds` 已经提供了祖先链，不需要新数据。

### 4.4 三层试听

一个播放条，四个按钮：`全奏 / 只留鼓 / 只留低音 / 只留旋律`。

这是把「音色与构成」从形容词变成动作的关键。用户听到「低音在反拍上」，可以立刻把鼓关掉，只听低音，确认什么叫反拍。实验室的七层开关已经验证过这个交互是有效的，这里只是把它下放到单个风格。

配色沿用现有语义：播放中激光洋红，solo 冰蓝，其余琥珀。

### 4.5 原曲出口

合成示例之后必须有一步「去听真的」。不做托管，只做搜索深链：

```
https://search.bilibili.com/all?keyword={artist} {title}
https://music.163.com/#/search/m/?s={artist} {title}
```

条目页现有 `examples` 列表（1255 条有条目例曲）已经有歌名和艺人，直接拼 URL 即可。这样既合规又比现在「只有文字索引」多一步。

### 4.6 最大的风险：听起来都像同一个合成器

这是本方案最可能失败的地方。60 段都用同一套振荡器和同一套鼓，用户听完三段就会说「这不是都一样吗」。

三条对策，缺一不可：

1. **差异要夸张**：不是把 cutoff 从 900 调到 1100，而是把 kick 的 pitch 从 170 打到 48、把失真开到 30、把混响从 0 拉到 0.45。宁可过火，不要含蓄。
2. **每段必须有一个「签名动作」**：Techno 的 acid 滑音、Trance 的 riser、Dubstep 的 wobble、Hardstyle 的反向 bass。人记住的是动作，不是参数。
3. **必须有「去听原曲」的出口**，并且在文案里主动承认：「这是骨架，不是原曲。真正的质感在录音里。」

验收方式：找 5 个没听过这些风格的人，放 6 段，让他们两两配对说「哪两段最像」。如果配对准确率 < 60%，说明差异不够，回去改配方。

## 5. 分享：一张卡，不是一条链接

### 5.1 微信里的三个技术事实

| 事实 | 后果 | 应对 |
| --- | --- | --- |
| 微信内置浏览器基本不支持 `navigator.share` | 不能调系统分享 | 生成图片，引导长按保存 |
| 只有 `<img>` 长按才有「保存图片」，`<canvas>` 没有 | 直接画在 canvas 上等于白做 | 必须 `toDataURL()` 后塞进 `<img>` |
| 链接预览（标题 / 缩略图）来自 HTML 的 `og:` 标签，SPA 的 hash 路由拿不到 | 所有分享看起来一模一样 | 预渲染 60 个静态壳页 |

### 5.2 卡面结构（1080 × 1440）

```
┌────────────────────────────────────┐
│ FIELD NOTES / 001            ▮▮▮▮ │  编号 + 电平装饰
│                                    │
│ TECHN0                             │  风格名（窄体，96px）
│ 科技舞曲                            │  中文（30px）
│                                    │
│ 132 ──────────●──────────          │  BPM 大字 + 60–180 刻度
│ BPM           快 / 想抬脚           │  速度带用体感词，不用术语
│                                    │
│ 一条不会停的传送带，                 │  L1（36px，最多两行）
│ 你只能跟着走。                      │
│                                    │
│ ① 鼓    每拍一脚，几乎没有起伏        │  三个听点，等宽标签
│ ② 低音  在反拍上一下一下             │
│ ③ 空间  很干，几乎没有混响           │
│                                    │
│ 凌晨两点以后，灯全灭的时候           │  场景句
│                                    │
│ ┌────┐  扫码听 8 秒                 │  QR（本地生成）
│ │ QR │  em.fm/s/techno             │  短链，不带 #
│ └────┘                             │
│ 电音档案 · 不做标准答案              │  品牌条
└────────────────────────────────────┘
```

四个设计决定：

- **BPM 放最大**，因为它是唯一一个可以拿来对照自己感受的数字。
- **不放流派史**。史是读完才需要的，不是决定要不要读的理由。
- **场景句必须有**。它是非专业听众的钩子：「凌晨两点以后」比「130–140 BPM，4/4 拍」有用一百倍。
- **二维码指向短链不带 `#`**：`/s/techno` 由 nginx 302 到 `/music/#/genre/g-xxxx`。`#` 后面的内容不会发给服务器，所以短链必须是路径形式。

### 5.3 三种卡，各有用途

| 类型 | 版式 | 用途 | 传播力 |
| --- | --- | --- | --- |
| 单风格卡 | 1080×1440 | 群里回答「这什么风格」 | 中 |
| **对比卡** | 1080×1080 左右分栏 | 「同一 BPM 的两张脸」：Techno 132 vs Trance 138；Trap 140 vs Hardstyle 150 | **高**，因为有辨论点 |
| Set 曲线卡 | 1080×1350 | DJ 把 60 分钟的速度曲线发给主办方/群 | 中高，工具属性强 |

对比卡是这个方案里最值得先做的一张。它不需要用户已经懂，只需要用户好奇：

```
┌─────────────────┬─────────────────┐
│ TRAP            │ HARDSTYLE       │
│ 140 BPM         │ 150 BPM         │
│                 │                 │
│ 听起来像 70      │ 听起来像 170     │
│ 两拍一下         │ 每拍一脚         │
│ 头会自己点       │ 每一脚踹在胸口   │
│                 │                 │
│   [听 A]        │   [听 B]        │
└─────────────────┴─────────────────┘
```

### 5.4 工程要点

- 尺寸固定 1080×1440（3:4），微信群预览清晰，朋友圈不被裁。
- Canvas 里的字体必须显式写全 `font` 字符串（canvas 不继承 CSS），中文用系统字体栈，标题用 Bahnschrift，数字用等宽。
- 二维码本地生成（引一个 ~15KB 的 `qrcode` 到 `vendor/`），不请求第三方，离线也能出图。
- 导出后同时给两个出口：`<img>`（长按保存）+ `<a download>`（安卓/桌面直接下载）。
- 卡片文案进 canvas 前做一次长度校验，超长截断并打日志——比上线后发现溢出好。
- 生成耗时目标 < 120ms，点击即出，不做 loading。

### 5.5 OG 预渲染

hash 路由拿不到预览，所以在构建期生成静态壳：

```
dist/g/techno/index.html
  <meta property="og:title" content="Techno / 科技舞曲 · 132 BPM">
  <meta property="og:description" content="一条不会停的传送带，你只能跟着走。">
  <meta property="og:image" content="https://…/og/techno.png">
  <script>location.replace('/music/#/genre/g-2077')</script>
```

`og:image` 用同一套 Canvas 逻辑在 Node 里跑一遍（`node-canvas`）生成，一张卡两用：分享图和预览图同源，不会出现「图和内容对不上」。

先在 Top 60 风格上做，其余走默认图。微信对 `og:image` 的要求按经验是 300×300 以上、尽量 < 300KB，上线前实测。

### 5.6 传播路径

不是「发一条微博等人来」，而是**在对话发生的地方提供答案**：

1. 群里有人问「这什么风格」→ 有人回一张卡 → 卡上有二维码 → 扫码听 8 秒。
2. DJ 发「今晚 128，先听这个」→ 附一张 Set 曲线卡 → 群友点二维码。
3. 对比卡被转发到「这俩到底有什么区别」的争论里。

三种都发生在微信群里，都不需要用户先打开网站。这是「轻量讲解形式」的真正含义：**讲解必须能在不打开网站的情况下完成**。

## 6. 听歌识曲：可行性与分期

### 6.1 结论

**完整的「识别具体曲目」在纯静态站不可行**，必须后端 + 商业指纹库，而且它并不能真正解决用户的问题。**真正该做的是「识别特征」而不是「识别曲目」**，而且它不需要后端，可以在浏览器里完成。

理由在下一节。

### 6.2 四条路线

| 路线 | 精度 | 成本 | 需要后端 | 工期 | 判断 |
| --- | --- | --- | --- | --- | --- |
| A. ACRCloud / AudD 等商业 API | 曲目级很高（主流曲库） | 约 $20–50 / 万次，需询价，有试用 | **是**（密钥不能放前端） | 3–5 人日 + 运维 | 可选，P2 |
| B. ShazamKit | 高 | 免费 | 否，但**仅原生 App** | — | 不可行 |
| C. 浏览器内自建指纹库 | — | 需参考曲库 | 是 | — | 不可行 |
| D. **浏览器内特征分析**（BPM / 律动 / 低频形态） | 中（BPM ±2 可靠） | 0 | **否** | 3–4 人日 | **推荐，P1** |

### 6.3 为什么「特征识别」更对症

这是本方案里最需要说清的一个判断。

**缺的那一层是「曲目 → 风格」的映射，而本站没有这个库。**

本站有的是「风格 → 解释」（1376 条）和「风格 → 配方」（60 条）。ACRCloud 返回的是 `title / artist / album`，它不返回风格。要拿到风格，还得再去 Beatport / SoundCloud / 网易云查 genre 标签——这一步要么不可靠（同一首歌在不同平台标签不同），要么要爬（合规风险），要么要买（另一笔钱）。

于是「识曲」的真实链路是：

```
录音 → 商业 API → 歌名 → 查外部 genre 标签 → 落到本站条目
                  ↑ 这一步不可靠，也可能查不到（地下曲目尤其）
```

而「特征识别」的链路是：

```
录音 → 本地分析 → BPM + 律动型 + 低频形态 → 候选 3 个风格（带试听确认）→ 条目页
```

**更短、更可靠、更可解释，而且过程本身就是科普。** 用户看到「我听到的是每拍一脚，132 左右，低音一直在垫着 → 可能是 Techno / Hard Groove / Trance」，这比「这是某某的歌」更有教育价值。

还有一个现实考虑：电子音乐里大量是 white label、未发行、DJ 改编版本，商业指纹库的命中率在这个场景下明显低于流行曲。而 BPM 和律动是**录音本身的属性**，不管有没有发行都能测。

### 6.4 P1 技术方案

| 步骤 | 做法 | 精度预期 |
| --- | --- | --- |
| 采音 | `getUserMedia` 或 `<input type="file" accept="audio/*">`，取 10–15 秒 | — |
| 降噪 / 带通 | 简单带通 60–4000Hz，去掉人声和噪声 | — |
| BPM | onset 检测 + 自相关（或引入 `web-audio-beat-detector`，约 8KB） | ±2 BPM，可信 |
| 律动型 | 用检测到的 beat 网格算 kick 能量落点：正拍占比 > 80% → 每拍一脚；两拍一组 → 半拍；不规则 → 碎拍 | 4 类里 3 类可靠 |
| 低频形态 | 低频段（<150Hz）能量包络的占空比 | 三分类，够用 |
| 映射 | 三个特征查 `listen.js` 的 band / groove / lowEnd，取交集 | 候选 3–5 个 |
| 呈现 | **不给结论，给候选 + 试听**，让用户自己确认 | 避免过度承诺 |

关键设计：**输出是「可能」，不是「答案」**。UI 写「听起来像这三个」，每个候选带 8 秒试听和一个「就是这个」按钮；用户点「就是这个」后落库，成为下一次映射的先验。

隐私：录音不上传，全程在 `AudioContext` 里，页面明确写「不会上传」。这既是卖点，也省掉了合规成本。

可选的增强：引入 `Essentia.js`（WASM，约 2.5MB，含 TempoCNN 与 MusiCNN 模型，模型 0.1–4.7MB）可以在浏览器里做更准的 tempo 与「是不是电子乐」的二分类。但它自带 9–10 个西方大类（electronic / rock / pop…），映射不到本站 24 族，且 2021 年的基准里端到端推理要 3.7–28 秒、移动端更慢。**建议只在 P1 的 BPM 环节按需加载 TempoCNN，不引入整包。**

### 6.5 P2：商业 API 的成本与合规

如果后续确实要做「曲目识别」（比如用户想收藏某首歌），再加 ACRCloud：

- 需要一台小机器或 Serverless 做代理（密钥不能进前端），多一个运维面；
- 约 $20–50 / 万次（公开资料口径，商务价需询价），个人站量级下每月几十美元；
- 结果仍然只给歌名，**必须再解决 genre 映射**，否则对本站价值有限；
- 建议形态：「识别到曲目 → 用 artist + title 在站内搜索 → 如果本站有条目就跳，没有就提示『这条还没收录』」。这样至少把「未收录」变成一个真实的内容缺口列表。

### 6.6 明确不做

- 不做「实时识曲」常驻监听（耗电、隐私、误报）。
- 不承诺「一定能认出来」。
- 不为识曲单独做 App——小程序也不做，成本远超收益。

## 7. DJ 实用功能

五个功能，共同点：**都是「在台上或准备上台时」会用到的东西，而且每一个都能回链知识库**。这是本方案对「联动」的定义——不是页面上互相加个链接，是工具的输出来自知识库的字段。

### 7.1 过渡检查器（Transition Check）

选 A、B 两个风格，输出四行判断 + 三条动作。

| 判据 | 阈值 | 输出 |
| --- | --- | --- |
| BPM 差 | ≤ 3% | 「直接 mix」 |
| | 3%–8% | 「需要 pitch ±x%，人声会变调」 |
| | 半速/双速关系 | 「half-time 叠 mix，不要对拍」 |
| | > 8% | 「不要接，中间垫一首」 |
| 律动 | 同型 | 「可以对小节线切」 |
| | 四拍 ↔ 碎拍 | 「用 8 小节鼓过渡，别硬切」 |
| 低频 | 都「一直垫着」 | 「先切 A 的低频，再进 B 的 kick」 |
| | 一方「几乎没有」 | 「B 进来时会突然变满，留 4 小节」 |
| 同族 | 同一大族 | 「可以直接叠 16 小节做 layer」 |

每条动作后面挂两个链接：`transitions` 课时（现有 22 课之一）和对应术语条目（`#/search?q=EQ`）。这样「在台上想到的问题」能一路走到「为什么会这样」。

### 7.2 BPM 邻接表

给定一个风格或一个 BPM 数字，列出：

- ±3 BPM 内、同律动的风格（可以直接接）
- ±3 BPM 内、不同律动的风格（可以接，但要过渡）
- 半速 / 双速对应的风格（70 ↔ 140）

这是 Set 编排最常用的查询，数据全部来自 `listen.js`，不需要新内容。做成一张表比做成搜索框好用——DJ 在台上没空打字。

### 7.3 现场速查卡（离线）

- 一屏一个风格，字号 ≥ 28px，暗色，无滚动。
- 左右滑动切风格，双击回到矩阵。
- Service Worker 缓存 `index.html` + 4 个 data 文件（约 1.5MB），俱乐部信号差也能开。
- `navigator.wakeLock` 保持屏幕常亮（有就用，没有就降级）。
- 只显示 L1 + 三个听点 + BPM，不显示正文。

这是「把网站当工具用」的最小实现。验收标准很硬：**飞行模式下打开，10 秒内看到某个风格的 BPM。**

### 7.4 Set 曲线

拖 8 个风格到一条 0–120 分钟的时间轴上，自动生成速度曲线，导出成图片（复用分享卡的渲染器）。

用途有两个：发给主办方对齐预期；发到群里做预告。第二个用途让它自带传播。

### 7.5 三步判定

三个问题，每次 4 个选项：

1. 鼓是每拍一脚、两拍一下、碎的，还是拖着的？
2. 低音是一直垫着、一下一下，还是几乎没有？
3. 有人声在唱吗？

8–16 个分支，落到 ≤ 5 个候选，每个候选带试听。这是「不知道这是什么」的最短路径，也是三问入口的现场版（入口版按 BPM 分，这个按特征分，互为补充）。

### 7.6 功能总表

| 功能 | 数据依赖 | 回链 | 工作量 |
| --- | --- | --- | --- |
| 过渡检查器 | `listen.js` 的 bpm / groove / lowEnd | `transitions` 课时 + 术语条目 | 2 人日 |
| BPM 邻接表 | 同上 | 风格条目 | 1 人日 |
| 离线速查卡 | `listen.js` + SW | 条目页 | 2 人日 |
| Set 曲线 | `listen.js` + 卡片渲染器 | — | 2 人日 |
| 三步判定 | `listen.js` + 配方池 | 条目页 + 练习 | 1.5 人日 |

### 9.1 一个必须先做的前置

**域名 + HTTPS（0.5 人日）**。

- 微信里 `http://IP` 会带风险提示，转化直接掉一半；
- 没有备案域名就无法配置公众号 JS 安全域名，后续所有「自定义分享卡片」的路都堵死；
- 二维码印在贴纸上必须是 https，否则 iOS 相机识别后可能不直接打开。

这件事排在 Sprint 1 之前，不属于任何冲刺，但决定后面所有传播动作的效果。

### 9.2 验收脚本

沿用现有 `scripts/regression/` 的分层思路，新增 `check-listen.mjs`：

| 断言 | 判定 |
| --- | --- |
| 24 大族都有 `band / groove / fp` | 缺一个即失败 |
| 每个配方能被 `OfflineAudioContext` 渲染出非静音 | RMS > 阈值 |
| L1 字数 ≤ 18、`hear` 恰好 3 条 | 逐条检查 |
| 60 个高频风格的 `bpm.source` 非空 | 缺即失败 |
| 分享卡 canvas 非空白（采样 20 个像素点） | 全黑即失败 |
| 所有 `entryId` 在 `kb.js` 中存在 | 防止改名后静默失效 |

最后一条尤其重要：`kb.js` 重新生成后 id 可能变化（原文行号变了），`listen.js` 会静默指向不存在的条目。这个断言能把它变成构建失败而不是线上空白。

## 10. 推广建议

### 10.1 顺序：先做工具，再做内容

先发「过渡检查器」和「Set 曲线」，再发风格卡。理由：**工具会被 DJ 主动转发，内容不会**。一个 DJ 转发「这个能查两首歌能不能接」，是在展示自己的专业；转发「这是一个电音科普站」，是在做公益。前者的动力强得多。

工具起来之后，风格卡才有落地的场景——群里有人问，才有人答。

### 10.2 四个渠道与具体动作

| 渠道 | 动作 | 频率 | 成本 |
| --- | --- | --- | --- |
| 俱乐部群 / DJ 群 | 每周一张对比卡 + 一句「这俩你能听出区别吗」 | 每周 1 次 | 0 |
| 小红书 / B 站竖屏 | 15 秒：同一段 loop 切 3 个风格，字幕只写 BPM + 一句人话 | 每周 1 条 | 1 小时/条 |
| 线下 | 二维码杯垫 / 贴纸，放 3–5 家合作场地 | 一次性 | 0.3–0.8 元/张 |
| 校园社团 / 工作坊 | 「1 小时听懂 6 种 House」，现场用矩阵讲到哪点到哪 | 每月 1 次 | 场地 |

线下物料上的二维码必须指向**对比卡落地页**而不是首页——首页对现场的人是迷宫。

### 10.3 八周内容日历

| 周 | 主推 | 素材 |
| --- | --- | --- |
| 1 | 三问入口上线 | 一张「140 的 Trap 和 150 的 Hardstyle」对比卡 |
| 2 | House 五兄弟 | Deep / Tech / Bigroom / Afro / Amapiano 五连卡 |
| 3 | Bass 家族 | Dubstep / DnB / Trap 三联 |
| 4 | Trance vs Techno | 对比卡 + 30 秒 A/B 视频 |
| 5 | HDM | Hardstyle / Uptempo，配「为什么它听起来最快」 |
| 6 | 非舞池 | Ambient / Breakcore / Hyperpop，明确「不在俱乐部」 |
| 7 | DJ 工具 | 过渡检查器 + Set 曲线 |
| 8 | 识曲 P1 | 「录 10 秒，告诉你这是什么」 |

### 10.4 指标

不装第三方统计（隐私 + 体积），自建一个 1.5KB 的 beacon 打到自己服务器，只采 6 个事件：

| 事件 | 含义 | 目标（首月） |
| --- | --- | --- |
| `listen_play` | 第一次听到声音 | 入口页 60% |
| `card_generate` | 生成分享卡 | 每日 ≥ 30 |
| `share_copy` | 复制/保存卡 | 生成数的 40% |
| `qr_land` | 扫码落地（带 `?s=` 参数） | 每周 ≥ 200 |
| `transition_check` | 用了过渡检查器 | 每周 ≥ 50 |
| `kb_from_listen` | 从听感页进条目页 | 30% |

**北极星：从进入到第一次听到声音的转化率。** 现在这个数大概很低——首页主按钮通向文字课，不是声音。这个指标直接对应用户的核心抱怨。

反面指标：图谱页跳出率。如果加完入口它还是高，说明分类树作为入口确实不成立，可以进一步降级。

### 10.5 不要做的推广

- 不买量。目标人群太窄，投放 ROI 为负。
- 不做「1376 种风格大全」这种标题。它吸引来的是收藏党，不是使用者。
- 不在没有域名的情况下印二维码。
- 不追热点风格。风格的生命周期比内容生产周期短。

## 11. 风险清单

| 风险 | 触发信号 | 对策 |
| --- | --- | --- |
| 合成试听听起来都一样 | 用户说「这不是同一个声音吗」 | 拉大差异、加签名动作、必须给原曲出口（§4.6） |
| BPM 推断被当成事实 | 有人在群里指出「这首不是 128」 | `source` 三值必显示；推断值只给区间不给单点 |
| 分享卡文案出错被传播 | 卡片上的描述与常识冲突 | 卡片文案走一次人工审，不进自动流程 |
| `listen.js` 与 `kb.js` 失联 | 条目改名后卡片空白 | 构建断言 entryId 存在（§9.2） |
| 微信里长按存不了图 | iOS 实测失败 | 必须是 `<img>` 不是 canvas；真机验收 |
| 移动端首屏变慢 | 首屏 > 2s | 配方是数据不是音频；按需构建音频图；`listen.js` 延迟加载 |
| 识曲精度不达预期 | 用户测 10 次错 6 次 | 输出「可能」不给结论；先只承诺 BPM |
| 导航改四项后老用户迷路 | 制作课入口点击下降 | 保留页脚与首页的旧入口；观察两周再收 |
