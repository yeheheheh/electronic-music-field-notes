# 动手模块实现方案：从 22 节课到一首完成曲

> 目标：为每个学习章节构建内容严格对应的动手模块，模块之间可自由切换且不丢状态，最终能在站内产出一首属于自己的简单电音。

## 0 结论摘要

| 项 | 结论 |
| --- | --- |
| 模块数 | **9 个**（现有 6 个 → 新增 3 个：信号链、混音、导出） |
| 与章节的关系 | 模块 ↔ **阶段**（8 个阶段，其中阶段 04 拆为两个模块）；任务 ↔ **课时**（22 节课全部有落点） |
| 划分依据 | 九个**可控维度**，全部从知识库三条主线推导（信号链 / 频段 / 时间），不是人为切分 |
| 边界规则 | **数据所有权**：一个模块只拥有一个维度的写权限，跨维度影响通过派生实现 |
| 切换方式 | 四种入口 + 线性引导但**不锁定**；切换时**不中断音频** |
| 状态模型 | 三层：工程数据（共享）/ 模块视图（各自）/ 会话（跨模块连续） |
| 产出 | 站内离线渲染导出 **WAV**，长度由结构模块排出的段落总长决定 |
| 前置重构 | 两处（调度函数抽离、门控纯函数化），约 120 行改动 |

## 1 现状诊断

### 1.1 三个硬缺口

我把 `data/course.js` 的 22 节课与 `app.js` 的 `LESSON_STUDIO` 映射逐条对照后，确认三个缺口：

**缺口一：模块数与章节数不对等。** 现有 6 个模块要服务 22 节课，密度严重不均：

| 现有模块 | 服务课时数 | 说明 |
| --- | --- | --- |
| `sound` | 7 节 | 从音色设计一直管到混音、导出，跨度太大 |
| `beats` | 5 节 | 从「建工程模板」到「House 项目」都塞在这里 |
| `bass` | 3 节 | — |
| `song` | 3 节 | — |
| `chords` | 1 节 | — |
| `melody` | 1 节 | — |

`sound` 模块同时承担「振荡器波形」「滤波共振」「增益结构」「EQ 让位」「混响空间」五种完全不同的操作——它已经不是模块，是一个杂物间。

**缺口二：两节课没有任何模块。**

| 课时 | 阶段 | 现有互动 | 问题 |
| --- | --- | --- | --- |
| `signal-chain-basics` | 00 准备 | `type: "none"` | 纯阅读，无音频 |
| `sampling-chops` | 04 旋律与音色 | `type: "lab"` | 只能开关七组音色，与「切片」无关 |

这两节课在 `LESSON_STUDIO` 里被刻意留空（第七轮的注释说明是「硬套会误导」）。留空的判断是对的，但结果是这两节课的动手环节在站内**无处可去**。

**缺口三：站内没有导出能力。**

`finish-export` 的交付物写着「一个 2 分钟 Demo（WAV/MP3）+ 一份 5 行复盘」，但全站搜索 `OfflineAudioContext` / `encodeWav` / `导出` 无任何实现。**「产出一首属于自己的电音」目前无法在站内兑现**——用户只能把参数抄进自己的 DAW。

### 1.2 知识库的内容供给上限

这是设计新模块时最需要正视的约束。知识库的制作类内容**总共 6 篇、约 2800 字**：

| id | 标题 | 字数 | 可动手颗粒度 |
| --- | --- | --- | --- |
| `guide:production-structure` | EDM 结构：拍、小节、乐句、乐段与八段结构 | 869 | **高**：八段各带小节数区间与层数规则 |
| `guide:production-instrument-summary` | 七大乐器组：七组音色怎么分工 | 690 | 中：七组角色 + 出现段落 |
| `guide:production-signal-chain` | 音色是怎么来的：MIDI → 音源 → 效果器 → 总线 | 661 | **高**：四步链路 + 合成器四步 + 四类效果器 |
| `guide:production-practice` | 拆歌练习 | 279 | **高**：四步动作，带 8 小节 / 60–120 Hz 等具体数字 |
| `guide:production-frequency` | 频谱：七个乐器组不要挤在同一条线上 | 216 | **高**：Sub/Low/Mid/High 的具体 Hz 边界 |
| `guide:production-caveat` | 结构不是公式 | 86 | 无操作内容 |

外加 7 篇 `instrument:*`（七组音色，每篇带「怎么听」的听辨动作）。

**三处内容错配，正好落在要新增的模块范围里：**

1. 知识点 #44「导出与响度」指向 `guide:production-caveat`——该文档全文 86 字，讲的是「结构不是公式」，**不含任何导出、响度、LUFS 内容**。
2. 知识点 #35「增益与 Headroom」指向 `guide:production-signal-chain`——该文档**不含任何增益、dBFS、headroom 内容**。
3. `guide:production-instrument-summary`（七组音色主文档）**未被任何阶段的 `knowledge` 字段引用**，只出现在 `project-house` 的 `kbLinks` 里。而七组音色正是混音模块的核心依据。

**知识库明确缺失的主题**（做新模块时必须自建内容，不能假装有依据）：

| 缺失主题 | 对应课时 | 现状 |
| --- | --- | --- |
| 增益结构 / Headroom / dBFS | `gain-stage` | 无任何文档 |
| 自动化（Automation） | `automation-energy` | 无 automation 条目 |
| 导出与响度（LUFS / 限幅） | `finish-export` | 无，且被错配 |
| 立体声 / Pan / 单声道兼容 | `space-stereo` | 无 stereo / pan 条目 |
| 压缩参数（ratio / attack / release） | `eq-space`、`gain-stage` | `glossary:compressor` 仅 48 字，无参数 |
| 采样切片操作（切片点 / transient / warp） | `sampling-chops` | 仅 4 条共约 176 字的零散术语 |
| 效果链推荐顺序模板 | `signal-chain-basics` | 只有「顺序会改变结果」的原则，无模板 |

**这决定了方案的一个硬边界**：新增的混音、导出模块**不能只做「知识库的可视化」**，必须自带一份最小的操作规范（放在模块内的说明文案里），否则用户在知识库查不到依据。方案 §8 会把这条列为风险。

## 2 模块划分依据与边界

### 2.1 划分依据：九个可控维度

划分不按「课时数平均分」，而是按**用户在制作中可以独立做决定的维度**。这个依据从知识库本身推导：

知识库给了三条主线：

- `guide:production-signal-chain`：**声音从哪来、经过什么**（MIDI → 音源 → 效果器 → 总线）
- `guide:production-frequency` + 7 篇 `instrument:*`：**有哪些声音、各占哪段频段**
- `guide:production-structure`：**声音什么时候出现**（拍 → 小节 → 乐句 → 乐段）

把这三条主线展开，得到三个正交轴 + 三个贯穿轴：

```text
贯穿轴 ── 信号链（拓扑）  音色（音质）  输出（成品）
            │              │             │
正交轴 ── 频段 × 时间 ─────┴─────────────┘
            │
            ├─ 频段：低音(20–250Hz) / 和弦(250Hz–2kHz) / 旋律(中高频)
            └─ 时间：节拍(step 分辨率) / 结构(bar 分辨率)
```

**为什么节拍与结构是两个模块而不是一个**：它们工作在知识库给出的**不同时间单位层级**上。`guide:production-structure` 明确列了四级——Beat（拍）→ Bar（小节）→ Phrase（乐句）→ Section（乐段）。节拍模块工作在第 1–2 级（16 分音符网格、单小节），结构模块工作在第 3–4 级（8 小节乐句、段落编排）。时间分辨率不同，操作方式也不同（点格子 vs 拖段落块）。

**为什么低音、和弦、旋律是三个模块而不是一个「音高」模块**：它们占据不同频段（对应 `guide:production-frequency` 的 Sub/Low/Mid/High），且与 Kick 的竞争关系各不相同——低音要和 Kick 抢 20–250 Hz，和弦在中频，旋律在中高频。合成一个模块会让「频段让位」这个核心概念无处安放。

**为什么音色与混音是两个模块**：

| | 音色模块 | 混音模块 |
| --- | --- | --- |
| 作用对象 | **总线**（一个全局效果链） | **每一层**（各自的电平 / EQ / 声像 / 发送） |
| 回答的问题 | 「这个 Loop 整体是什么性格」 | 「这几层之间谁让谁」 |
| 改动的结果 | 六层同时变化 | 层与层的相对关系变化 |
| 知识库锚点 | `guide:production-signal-chain` 的合成器四步 | `guide:production-frequency` 的「互相让位」 |

**为什么阶段 04 要拆成两个模块**：「旋律与音色设计」包含 `lead-hook`（写旋律线）和 `synth-controls` / `sampling-chops`（改音质）。前者是**音高序列**问题，后者是**频谱与包络**问题，操作性质完全不同（网格点音 vs 推子调参）。

### 2.2 边界规则：数据所有权

模块要能自由切换且不互相打架，必须有明确的所有权。规则只有一条：

> **一个模块只拥有一个维度的写权限；其他维度对它的影响，通过派生规则自动实现。**

这条规则解释了现有的一个优秀设计：低音模块**不拥有和弦数据**，它只存相对偏移（`[0, 7, 12]`），根音由 `chords[bar]` 派生。所以改和弦时低音自动跟着走，而低音模块本身完全不需要知道和弦模块的存在。

按这条规则展开九个模块的所有权：

| 模块 | 拥有的数据 | 只读依赖 | 派生方向 |
| --- | --- | --- | --- |
| 01 信号链 | `chain[]`（效果器顺序） | — | → 全局音质 |
| 02 节拍 | `drums{kick,clap,hat,openhat}`、`swing` | — | — |
| 03 低音 | `bass[3][16]`（和弦音偏移） | `chords[bar]` | 根音 ← 和弦 |
| 04 和弦 | `chords[4]` | — | → 低音根音、旋律调内 |
| 05 旋律 | `melody[8][16]`（音阶级数） | `scaleIntervals`、`base` | 音高 ← 音阶 |
| 06 音色 | `sound{}`（滤波/失真/延迟/混响/音色） | — | → 全局音质 |
| 07 结构 | `structure[]`（段落 + 小节数） | 六层内容 | → 播放时的层门控 |
| 08 混音 | `mix{}`（每层电平/EQ/声像/发送） | 七层划分 | → 层间平衡 |
| 09 导出 | 无（只读全部 + 写 `export{}` 元信息） | `project` 全部 | — |

**边界的两条例外**（必须显式声明，否则会互相打架）：

1. **音色模块的总线效果 vs 混音模块的每层发送**：混音模块的「混响发送量」是**每层往总线混响送多少**，音色模块的「混响」是**总线混响本身的量**。两者相乘，不冲突。实现上：音色模块改 `reverbSend.gain`（全局缩放），混音模块改每层的 send 增益。
2. **节拍模块的鼓 vs 混音模块的鼓层电平**：节拍模块改「哪一拍响」，混音模块改「响多大声」。同一层，不同维度，互不覆盖。

### 2.3 九个模块总览

编号按**制作流程顺序**（与课程的 8 阶段同序）：

| # | 模块 | id | 维度 | 对应阶段 | 课时数 | 状态 |
| --- | --- | --- | --- | --- | --- | --- |
| 01 | 信号链 CHAIN | `chain` | 贯穿·拓扑 | 00 准备与信号链 | 2 | **新增** |
| 02 | 节拍 BEATS | `beats` | 时间·step | 01 鼓组与律动 | 3 | 扩展 |
| 03 | 低音 BASS | `bass` | 频段·低频 | 02 低频与 Bass | 3 | 扩展 |
| 04 | 和弦 CHORDS | `chords` | 频段·中频 | 03 和弦与情绪 | 2 | 扩展 |
| 05 | 旋律 MELODY | `melody` | 频段·中高频 | 04 旋律与音色设计 | 1 | 沿用 |
| 06 | 音色 SOUND | `sound` | 贯穿·音质 | 04 旋律与音色设计 | 2 | 扩展 |
| 07 | 结构 SONG | `song` | 时间·bar | 05 编曲与能量 | 3 | 扩展 |
| 08 | 混音 MIX | `mix` | 贯穿·平衡 | 06 混音与空间 | 3 | **新增** |
| 09 | 导出 BOUNCE | `bounce` | 贯穿·输出 | 07 完成一首歌 | 3 | **新增** |

**id 兼容性**（已核实）：`beats` / `chords` / `bass` / `melody` / `sound` / `song` 六个 id 保持不变，所以现有 localStorage（`em-studio-v1`）里的 `project.module` 与 `done{}` 继续有效，不会因为改编号而丢失用户进度。新增三个 id：`chain` / `mix` / `bounce`。

进度机制也自动适配：`completion()` 遍历 `MODULES` 数组生成状态，所以模块从 6 个增到 9 个后，**进度环的分母自动从 `/6` 变成 `/9`**，旧用户的已勾选模块保持已勾选，只是总量变大。不需要写迁移代码。

## 3 章节 → 模块 → 任务映射

### 3.0 双层对应关系

用户要「一一对应」，但 9 个模块与 22 节课不是同层概念。方案用**双层对应**兑现：

```text
阶段（8）  ←一一对应→  模块（9，阶段 04 拆两个）
课时（22） ←一一对应→  模块内的任务步骤（每模块 1–3 步）
```

这样每一节课都能在某个模块里找到**具体的动手任务**，而模块数量与章节层级对齐。

**覆盖完整性已核验**（脚本对照 `data/course.js` 逐条检查）：

| 检查项 | 结果 |
| --- | --- |
| 22 节课是否都有模块落点 | ✅ 22/22 |
| 是否有课时被两个模块重复覆盖 | ✅ 无 |
| 是否有映射指向不存在的课时 | ✅ 无 |

每模块承担的课时数：`chain` 2、`beats` 3、`bass` 3、`chords` 2、`melody` 1、`sound` 2、`song` 3、`mix` 3、`bounce` 3。对比现状（`sound` 独担 7 节），最重的模块从 7 节降到 3 节。

### 3.1 模块 01 · 信号链 CHAIN（新增）

**对应课时**：`daw-and-tracks`（DAW、轨道与工程模板）、`signal-chain-basics`（MIDI、音源、效果器与总线）

| 课时 | 动手任务 | 完成判定 |
| --- | --- | --- |
| `daw-and-tracks` | 给五类轨道各分配一个声部（鼓 / Bass / 和弦 / Lead / FX），点轨道头试听该声部 | 五条轨道都有声部，点任意轨道头能听到对应声音 |
| `signal-chain-basics` | 拖拽重排四个效果器（失真 / EQ / 压缩 / 混响），A/B 对比顺序变化 | 至少拖动过一次，且听过两种顺序的差异 |

**功能范围**：
- 五条轨道（对应 `glossary:track` 的五类命名）+ 每条的试听按钮
- 一条可拖拽排序的效果器链（4 个节点）
- 一个 A/B 对比开关：记住「顺序 A」与「顺序 B」，一键切换
- 信号流动画：MIDI → 音源 → 效果器 → 总线，高亮当前经过的节点

**明确不做**：不编辑音符内容（节拍 / 旋律模块的事）；不改效果器参数（音色模块的事）——这里**只改顺序**。

**知识库锚点**：`guide:production-signal-chain` 的核心句「效果器像流水线，顺序会改变结果：**先失真后混响，和先混响后失真，是两种声音**」。这个模块就是把这句话变成可以亲手验证的操作——目前这句话在站内只是一段文字。

**数据结构增量**：

```js
chain: ['distortion', 'eq', 'compressor', 'reverb'],   // 顺序即数组顺序
chainTracks: { kick: 'drums', bass: 'bass', ... },     // 五类轨道 → 声部
```

**技术实现**：重排时重建 `connect()` 链。四个效果器都是已有节点的复用（`waveShaper` / `biquad` / `dynamicsCompressor` / `convolver`），只是连接顺序变化。

### 3.2 模块 02 · 节拍 BEATS（扩展）

**对应课时**：`drum-programming`、`groove-and-half-time`、`drum-processing`

| 课时 | 动手任务 | 完成判定 |
| --- | --- | --- |
| `drum-programming` | 16 格点 Kick / Clap / Hat / Open Hat，从四套预设起步 | 至少点亮 4 格 |
| `groove-and-half-time` | 拉 Swing 滑杆 + 把 Kick 位移到第 8 格，听 Half-time 效果 | Swing 拉过 30%，Kick 挪过位置 |
| `drum-processing` | Kick 三层叠（Click / Body / Sub）分别开关，加 Snare 处理量 | 三层都单独听过 |

**功能范围**：现有 4×16 网格 + 四套预设，**新增**：
- Swing 滑杆（0–60%，实时听感变化）
- Kick 三层叠开关（Click / Body / Sub 独立开关与增益）
- Snare / Clap 处理量（短 → 长，模拟 Decay 与 Room）

**明确不做**：不改鼓组音高（不是必需）；不做完整鼓合成器（会超出「层次」的教学范围）。

**知识库锚点**：`instrument:percussion` 的「怎么听」——「先找 Kick 的落点，再看 Clap / Snare 是否落在二、四拍，Hi-hat 是规整还是滚动」。

**数据结构增量**：

```js
drums: { kick, clap, hat, openhat },        // 已有
swing: 0,                                    // 已有
kickLayers: { click: true, body: true, sub: true },   // 新增
snareTone: { decay: 0.16, room: 0.2 },                // 新增
```

### 3.3 模块 03 · 低音 BASS（扩展）

**对应课时**：`kick-and-bass`、`bass-sound-design`、`low-end-control`

| 课时 | 动手任务 | 完成判定 |
| --- | --- | --- |
| `kick-and-bass` | 打开侧链让位开关，或把低音音符挪到 Kick 的缝里 | 听到「Kick 落下时低音退让」 |
| `bass-sound-design` | 低音音色四选一：Sub / Punch / Growl / 808 | 四种都听过 |
| `low-end-control` | Sub 单声道开关 + Kick/Bass 分频点 | 分频点拖动过，听过单声道差异 |

**功能范围**：现有 3×16 网格（根音 / 五度 / 八度，随和弦换根）+ **新增**：
- **侧链让位**：一个 0–100% 的 ducking 量，Kick 落点时低音自动压下去（`setTargetAtTime` 实现，实时可听）
- **音色四选一**：Sub（纯正弦）/ Punch（短促带点击）/ Growl（LFO 抖动）/ 808（长滑音）
- **Sub 单声道开关**：模拟「低频单声道」处理
- **分频点**：Kick 与 Bass 的分界频率，拖动能听到让位效果

**明确不做**：不做完整侧链压缩器参数（attack / release / ratio）——教学目标是「听出让位」，不是调压缩器。

**知识库锚点**：`instrument:bass-bassline` 的频段（20–250 Hz）+ `guide:production-frequency` 的「Low 60–250 Hz：贝斯与 Kick 的主体；**堆太多会浑浊**」。

**数据结构增量**：

```js

bassSidechain: 0,                            // 新增 0–1
```

**知识库锚点**：`guide:production-signal-chain` 的「合成器四步：振荡器 → 滤波器 → ADSR 包络 → LFO」——这个模块就是把这句话变成四个可调的推子组。

**数据结构增量**：

```js

soundLfo: { rate: 0, depth: 0 },                 // 新增
```

### 3.8 模块 08 · 混音 MIX（新增）

**对应课时**：`gain-stage`、`eq-space`、`space-stereo`

| 课时 | 动手任务 | 完成判定 |
| --- | --- | --- |
| `gain-stage` | 调每层电平，让总线留出余量（电平表变绿） | 总线峰值低于阈值 |
| `eq-space` | 每层三段 EQ（低 / 中 / 高），让频段占用图不重叠 | 至少两组不再抢同一频段 |
| `space-stereo` | 每层混响 / 延迟发送量 + 声像，做出「一个近、一个远、一个宽」 | 三层有不同的空间设置 |

**功能范围**：
- **七层通道条**（对应 `guide:production-instrument-summary` 的七组音色）：每层一个电平推子 + 三段 EQ + 声像 + 混响发送 + 延迟发送
- **频段占用图**：四段（Sub 20–60 / Low 60–250 / Mid 250–2k / High 2–20k）的实时占用条，直观显示「谁在抢谁的频段」
- **总线电平表**：峰值与余量指示，对应「留 headroom」
- **一键独奏 / 静音**：每层与总线的 S / M

**明确不做**：不做压缩器参数（ratio / attack / release）——知识库对此无内容，且教学收益低；不做频谱分析仪（频段占用图已经够用）。

**知识库锚点**：`guide:production-frequency` 的四段频段边界 + 结论句「好的混音不是每个组都响，而是**每个组在自己的频段里清楚，并且互相让位**」。频段占用图就是这句话的可视化。

**与音色模块的边界**（已在 §2.2 声明）：混音模块改**每层的相对关系**，音色模块改**总线的整体性格**。

**数据结构增量**：

```js
mix: {
  drums:    { level: 1, eq: { low: 0, mid: 0, high: 0 }, pan: 0, reverb: 0.1, delay: 0 },
  bass:     { ... },
  chords:   { ... },
  vocal:    { ... },
  lead:     { ... },
  ambient:  { ... },
  fx:       { ... },
},
```

**新增的七层从哪来**：现有音频引擎有六层（drums / bass / chords / melody / sound / song 是模块，不是层）。实际发声层是：kick / clap / hat / openhat（鼓组内 4 个 voice）、bass、chords、melody。混音模块按 `guide:production-instrument-summary` 的**七组音色**组织：打击乐 / 贝斯 / 和弦旋律 / 人声 / 主奏 / 氛围 / 音效。

其中「人声」与「音效」目前没有声音来源。方案：**人声层**接模块 06 的元音切片，**音效层**接模块 07 的转场元素（Riser / Impact）。这样七层都有实际内容，不是空推子。

## 4 模块切换的交互方式

### 4.1 四个入口

| 入口 | 位置 | 用途 | 现状 |
| --- | --- | --- | --- |
| **模块标签栏** | 顶部，9 个标签横向滚动 | 主入口，任意跳转 | 已有（6 个），扩展为 9 个 |
| **键盘 1–9** | 全局快捷键 | 熟手快速切换 | 已有（1–6），扩展为 1–9 |
| **上一模块 / 下一模块** | 走带区两侧 | 按制作顺序线性推进 | 新增 |
| **课程页「在这里动手」** | 课时页内嵌展开 | 从学习情境直接进入 | 已有（20/22），补全为 22/22 |

**第 5 个入口（推荐式）**：完成一个模块后，状态条出现「下一步：去写低音 →」。这不是强制流程，只是一个建议——它把「九个模块」变成一条**可跟随的路径**，但不锁门。

### 4.2 线性引导与自由切换

九个模块的编号本身就是制作顺序（信号链 → 节拍 → 低音 → 和弦 → 旋律 → 音色 → 结构 → 混音 → 导出）。设计原则：

- **默认给出顺序**：走带区的「下一模块」按钮、完成后的建议提示、模块标签栏的进度徽标，都在暗示「按顺序做」。
- **但不锁定**：任何模块随时可进。呼应现有的「课程不锁课」原则（`information-architecture.md` §8）。
- **软顺序由数据依赖形成**：如果用户跳过和弦直接写低音，低音会用默认和弦的根音（`Fm / Ab / Eb / Bb`）。等回头改和弦，低音自动跟着变。**用户不会因为跳过某一步而得到错误结果**——这是数据所有权设计的直接收益。

**移动端的标签栏**：现有 `.st-tabs` 用的是 `grid` 等分（桌面 6 列 → 移动端 3 列），**不是横向滚动**。9 个标签继续用等分会出问题：320px 屏幕上 3 列时每格约 100px，标签里的「编号 + 两字标签 + 英文副标题」三行内容会被挤扁。

方案改为：

| 断点 | 布局 | 说明 |
| --- | --- | --- |
| ≥ 1024px | 9 列等分 | 桌面一行放完，与现在的视觉语言一致 |
| 640–1023px | 5 列 × 2 行 | 保持等分网格，两行可接受 |
| < 640px | 3 列 × 3 行 | 保持等分网格；隐藏英文副标题，只留「编号 + 两字标签」 |

选择**保持等分网格而不是改横向滚动**的理由：等分网格下九个模块一眼全见，用户能立刻看到「有九步、我在第几步」；横向滚动会隐藏一半模块，与「按顺序推进」的引导相冲突。代价是移动端要占三行高度，但模块标签是核心导航，这个空间值得。

### 4.3 切换的连续性保证

「自由切换」要成立，必须做到三件事：

1. **音频不中断**。九个模块共用同一个 4 小节循环与同一套总线。切模块只换**控制面板**，不换声音。用户可以在节拍模块按下播放，切到低音模块继续写低音，鼓声一直在响——这才是「边听边改」。

2. **播放头不重置**。切换后新模块的面板立即反映当前播放位置（`paintPlayhead()` 在 `renderPanel()` 末尾调用，已有实现）。切换**不重启**音频会话。

3. **每层的音量与开关不因切换而变**。模块切换只影响 UI，不影响音频图。

**唯一需要停音频的情况**：进入导出模块渲染时。离线渲染不需要实时会话，但为了不让用户听到两个声音叠加，渲染前会暂停实时播放，渲染完恢复。

## 5 状态保持与恢复

### 5.1 三层状态模型

「不丢状态」需要先明确有哪些状态。方案分三层，各自的生命周期与持久化策略不同：

| 层 | 内容 | 生命周期 | 持久化 |
| --- | --- | --- | --- |
| **L1 工程数据** | `project`（drums / bass / chords / melody / sound / structure + 新增字段） | 跨会话 | `localStorage: em-studio-v1` |
| **L2 模块视图** | 每模块的滚动位置、折叠状态、当前选中项、A/B 暂存 | 跨会话（记住上次看到哪） | `localStorage: em-studio-ui-v1` |
| **L3 会话状态** | 播放 / 停止、播放头位置、当前 BPM | 仅当前页面 | 不持久化 |

**为什么 L2 要单独存**：现有实现只存 L1。用户切到结构模块滚到底部调完段落，切回节拍模块，滚动位置回到顶部——体验上的「丢失」。L2 是这次要补的。

**L3 为什么不持久化**：刷新页面后自动播放会违反浏览器的自动播放策略（需要用户手势）。刷新后回到「停止」状态是正确的。

### 5.2 派生规则表

「不丢状态」的深层含义是**跨模块的因果链不能断**。这些派生规则必须在切换时保持有效：

| 触发改动 | 自动派生 | 现有？ |
| --- | --- | --- |
| 改 `chords[bar]` | `bass` 根音跟着换（因为只存偏移） | ✅ 已有 |
| 改音阶 / 调性 | `melody` 音高跟着换（因为只存级数） | ✅ 已有 |
| 改 `sound{}` | 六层同时变化（总线效果） | ✅ 已有 |
| 改 `structure[]` | 播放时层门控跟着变 | ✅ 已有 |
| 改 `bassTone` | 低音 voice 换合成方式 | 🆕 新增 |
| 改 `mix.*.eq` | 该层频段占用图跟着变 | 🆕 新增 |
| 改 `chain[]` | 全局效果顺序变化 | 🆕 新增 |

**派生规则的设计约束**：派生必须是**单向的**，不能形成环。例如「和弦 → 低音根音」是单向的，低音模块**永远不写** `chords`。这条约束是模块能自由切换而不产生冲突的根本原因。

### 5.3 切换协议

模块切换的执行顺序（每一步都要做，顺序不能变）：

```text
switchModule(targetId):
  1. 落盘当前状态
     saveProject()                    // L1 写入 localStorage
     saveUiState(project.module)      // L2：记录滚动位置、折叠状态
  2. 更新模块标识
     project.module = targetId
     saveProject()
  3. 重渲染面板（音频不动）
     renderPanel()                    // 重建目标模块的 DOM
     bindPanel(targetId)              // 绑定该模块的交互
  4. 恢复目标模块的视图状态
     restoreUiState(targetId)         // L2：滚动位置、折叠状态、A/B 暂存
  5. 同步播放头
     paintPlayhead()                  // 立即反映当前播放位置
     refreshStatus()                  // 更新进度徽标与状态条
```

**关键点**：

- **第 1 步在改 `project.module` 之前**：否则会记录错模块的 UI 状态。
- **第 3 步不碰音频**：`renderPanel()` 只重建 DOM，不调用 `stopStudio()` / `startStudio()`。
- **第 5 步必须有**：新面板刚创建时所有格子都是「未点亮」状态，需要立即按播放头补上高亮，否则播放中切模块会看到一瞬间的空白。

**边界情况处理**：

| 情况 | 处理 |
| --- | --- |
| 播放中切换 | 音频继续；第 5 步补播放头高亮 |
| 切换时正在拖动（指针未抬起） | `pointercancel` 时结束绘制，再执行切换 |
| 内嵌模式（课时页）切换 | 内嵌模式只渲染单模块，**不提供标签栏**；切换通过「打开完整工作室」实现 |
| 目标模块 id 无效 | 回退到 `project.module` 的当前值，不改变状态 |
| localStorage 不可用（隐私模式） | 全部状态留在内存，切换仍正常，只是刷新后丢失 |

### 5.4 版本迁移

新增字段后，旧数据需要能平滑升级。现有 `loadProject()` 的策略是「顶层浅合并 + 嵌套对象显式深合并」：

```js
return {
  ...base,
  ...raw,                                          // 顶层：新字段自动取默认值
  drums: { ...base.drums, ...(raw.drums || {}) },  // 嵌套：显式深合并
  sound: { ...base.sound, ...(raw.sound || {}) },
  bass: Array.isArray(raw.bass) && raw.bass.length === 3 ? raw.bass : base.bass,
  // …每个嵌套结构都有一行
};
```

这个策略对**顶层新字段**天然友好（旧数据没有 `mix` / `chain` / `vowelChops` 时自动取默认值），但对**嵌套新字段不够**：如果 `raw.mix` 存在却缺少新增的层（例如以后从七层扩到八层），浅合并会让它保持缺失状态。现有代码对 `drums` / `sound` 都写了显式合并行，正是这个原因。

**所以新增的嵌套对象都要补一行显式合并**：

```js
mix:       { ...base.mix,       ...(raw.mix || {}) },
soundEnv:  { ...base.soundEnv,  ...(raw.soundEnv || {}) },
soundLfo:  { ...base.soundLfo,  ...(raw.soundLfo || {}) },
kickLayers:{ ...base.kickLayers,...(raw.kickLayers || {}) },
snareTone: { ...base.snareTone, ...(raw.snareTone || {}) },
```

**两处需要显式迁移的点**：

1. **`sound.chordVoice` 下沉到和弦模块**：读取时用 `chordTone ?? sound.chordVoice ?? 'pluck'` 回退，写入时只写 `chordTone`。旧数据不会丢设置。
2. **`version` 字段递增**：从 `1` 升到 `2`。加载时若 `version < 2`，做一次显式迁移（把 `sound.chordVoice` 复制到 `chordTone`），然后写回。这样迁移只发生一次，之后读取路径是干净的。

**迁移必须是幂等的**：重复执行不产生副作用。

## 6 产出路径：怎么得到一首电音

### 6.1 完整工作流

九个模块串起来就是一条完整的制作流程，与课程的 8 个阶段同序：

```text
01 信号链   搭好链路，理解声音从哪来
   ↓
02 节拍     写出鼓组（4×16 网格）
   ↓
03 低音     写低音线（自动跟随和弦根音）
   ↓
04 和弦     定和声进行（四小节）
   ↓
05 旋律     写一个动机（8 个音级数）
   ↓
06 音色     调整体性格（总线滤波 / 失真 / 空间）+ 元音切片
   ↓
07 结构     排段落（八段模板 + 转场 + 能量曲线）
   ↓
08 混音     平衡七层（电平 / EQ / 声像 / 发送）
   ↓
09 导出     渲染 → 试听 → 下载 WAV
```

**「属于自己的」如何体现**：用户的每一次点击、每一次拖动都写进同一个 `project` 对象，九个模块共享它。导出时渲染的就是这份数据——用户听到的成品里每一个音都是自己放的。两个项目模板（House / Trap）只是**起点**，不是成品。

**中途可以退出**：`project` 存在 localStorage，关掉浏览器再回来继续。这满足「不丢进度」的要求。

### 6.2 离线渲染方案

**技术可行性已验证**：`audio.js` 里所有音色函数（`kick` / `clap` / `hat` / `bass` / `chord` / `pad` / `lead` / `pluck`）都以 `session` 为第一参数，且都从 `session.ctx` 取音频上下文。这意味着**换一个上下文就能复用整套合成器**——不需要重写音频层。

**已核实的一处依赖**：`clap` 与 `hat` 的函数体里有一行 `noise.buffer = engine.noise`——它们引用了引擎预生成的 1.2 秒白噪声 buffer（`audio.js:117`）。这是**唯一的跨上下文依赖**，其余七个音色函数只碰 `session`。离线路径的处理方式：在 `OfflineAudioContext` 上重建一份同样长度的噪声 buffer 即可（同一段生成代码，换一个 ctx），约 6 行。

**渲染流程**：

```js
async function renderProjectToWav(project, { sampleRate = 44100, tail = 2.5 } = {}) {
  const totalBars = songTotalBars(project);              // 结构模块排出的总长
  const stepDuration = 60 / project.bpm / 4;             // 16 分音符时长
  const duration = totalBars * 16 * stepDuration + tail; // 尾巴留给混响衰减

  const ctx = new OfflineAudioContext(2, Math.ceil(duration * sampleRate), sampleRate);

  // 构造"离线 session"：只需实现音色函数用到的接口
  // 经核实，音色函数只碰 session.ctx / session.bpm / session.stepDuration /
  // session.track / session.gain / session.reverbSend，以及 clap·hat 用到的噪声 buffer。
  const offline = {
    ctx,
    bpm: project.bpm,
    stepDuration,
    active: new Set(),
    track(source, nodes) { this.active.add(source); },
    gain: ctx.createGain(),
    reverbSend: ctx.createGain(),
    noise: makeNoiseBuffer(ctx, 1.2),   // clap / hat 依赖，在离线 ctx 上重建
  };

  buildOfflineChain(offline, project);   // 复用 studioChain 的接线逻辑

  // 按绝对小节号逐拍调度（不是 4 小节循环）
  for (let bar = 0; bar < totalBars; bar += 1) {
    const gated = gateForBar(project, bar);              // 纯函数门控
    for (let step = 0; step < 16; step += 1) {
      const time = (bar * 16 + step) * stepDuration;
      scheduleStep(offline, gated, time, step, bar);     // 复用调度逻辑
    }
  }

  const buffer = await ctx.startRendering();
  return encodeWav(buffer);                              // PCM 16-bit
}
```

**WAV 编码**（纯手写，不需要库）：44 字节 RIFF 头 + 交织的 16 位 PCM 采样。双声道、44100 Hz。

**渲染时长**：按 32 小节、124 BPM 估算约 62 秒音频。离线渲染通常比实时快 5–20 倍，实际等待约 3–10 秒。渲染时显示进度提示（离线渲染没有进度事件，用「渲染中…」+ 骨架动画）。

### 6.3 两处必要重构

导出功能依赖两处重构，这两处同时修复现有隐患：

**R1：把 `startStudio` 里的 pattern 闭包抽成独立函数**

现在 `audio.js:1179` 的 `startStudio({ read })` 里，有一个约 100 行的 `pattern` 闭包，直接引用了 `read()`（读 UI 状态）。离线渲染无法复用。

改为：

```js
function scheduleStep(session, state, time, step, bar) { /* 原 pattern 体 */ }
```

实时路径传 `read()` 的结果，离线路径传 `gateForBar(project, bar)` 的结果。

**R2：把 `readForAudio()` 的结构门控抽成纯函数**

现在 `studio.js:263` 的 `activeLayers()` 依赖 `songClock`，而 `songClock` 由 `advanceSong(head)` 推进——`head` 来自 UI 播放头（`requestAnimationFrame` 驱动）。

这意味着**结构门控依赖 UI 帧率**。虽然音频本身不错位（门控是「读当前层」），但段落切换的时机受 UI 影响：如果 UI 掉帧，段落会晚一点切换。

改为纯函数：

```js
function gateForBar(project, bar) { /* 按绝对小节号返回门控后的 project */ }
```

实时路径用播放头算 bar，离线路径直接传 bar。**附带收益**：段落切换不再依赖 UI 帧率，且导出与实时播放的门控逻辑完全一致。

**改动量估算**：R1 约 80 行（移动代码，逻辑不变），R2 约 40 行（提取纯函数 + 两个调用点适配）。

## 8 风险与不做的事

### 8.1 三个真实风险

**风险一：知识库内容供给不足。** §1.2 已列出七个主题在知识库查无实据（增益、自动化、导出响度、立体声、压缩参数、切片操作、效果链模板）。新增的混音与导出模块**必须自带最小操作规范**，否则用户点开模块想「回查原理」时会扑空。

**建议同步修三处内容问题**（成本很低，收益直接）：

| 问题 | 建议 |
| --- | --- |
| 知识点 #44「导出与响度」错配到 `guide:production-caveat` | 新建 `guide:production-export`（导出流程、响度、限幅），或改指向 `guide:production-practice` |
| 知识点 #35「增益与 Headroom」错配到 `guide:production-signal-chain` | 同上，需补一篇讲增益结构的文档 |
| `guide:production-instrument-summary` 未被任何 `knowledge` 引用 | 提到阶段 06 的知识点里（它正是混音模块的核心依据） |

**风险二：模块数量增加导致移动端拥挤。** 9 个标签 + 走带 + 面板在 320px 屏幕上空间紧张。缓解：标签压缩为「编号 + 两字」、横向滚动、英文副标题在窄屏隐藏。需要在 P1 就做移动端验证，不能留到最后。

**风险三：离线渲染的听感与实时不一致。** 实时路径经过 `engine.master` → `analyser` → `destination`，离线路径要重建这条链。如果重建时漏掉某个节点（例如总线压缩器），导出结果会和用户听到的不一样。**缓解**：R1 重构的目的正是让两条路径共用同一套调度与接线逻辑；验证时要做 A/B 对比（同一工程，实时听一遍，导出的 WAV 听一遍）。

### 8.2 明确不做的事

| 不做 | 原因 |
| --- | --- |
| 真正的采样导入（上传音频文件、波形显示、切片点标记） | 工作量约等于其他所有模块之和；用共振峰合成元音替代，教学效果等价 |
| MP3 编码 | 需要引入编码器；WAV 无损且足够 |
| 云端保存 / 分享链接 | 站点无后端；`localStorage` 已满足「不丢进度」 |
| 锁课 / 强制流程 | 与现有「不锁课」原则冲突（`information-architecture.md` §8） |
| 撤销 / 重做 | 用户未要求；每个模块提供「重置本模块」按钮已足够 |
| 压缩器完整参数（ratio / attack / release） | 知识库无依据，教学收益低 |
| 频谱分析仪 | 频段占用图（四段）已能表达「让位」的概念，且更易读 |

### 8.3 一条设计原则的复述

这份方案的所有划分都遵守同一条规则：**一个模块只拥有一个维度的写权限，跨维度影响通过派生实现**。

它带来三个好处：
1. 模块可以自由切换而不互相覆盖——因为没有共享的可写数据。
2. 用户跳过某一步不会得到错误结果——派生会自动补上（跳过和弦，低音用默认和弦；回头改和弦，低音自动跟着变）。
3. 新增模块不需要改动已有模块——只要新模块声明自己拥有的数据与只读依赖。

这条规则不是新发明的，它是现有代码里已经存在的智慧（`bass` 只存偏移、`melody` 只存级数）。方案只是把它明确成规则，并推广到九个模块。
